The Bible Study App:
upgrade spec

This single file is the brief for an intensive update of the app in this repository. It holds the audit of what exists, the design tokens, ten screen mockups as real HTML with inline styles, the behaviour of each feature, the data model, and a phased build order with acceptance checks.

1 · Read first (instructions for the implementing agent)

  1. Work phase by phase, in the order of section 5. Finish, verify and commit one phase before starting the next. The app must build and deploy after every phase.
  2. Phase 1 is not optional and comes first. The database is currently open to anyone (section 3). No feature work before it is closed.
  3. The mockups are the visual source of truth. Each one in sections 7 and 8 is plain HTML with inline styles: read the markup for exact colours, sizes and spacing. They are static pictures of one state; the behaviour is in the notes beside each. Do not copy the mockup markup wholesale: rebuild it as components using the tokens in section 4.
  4. Keep the existing look. The app's "Journal" editorial theme (Instrument Serif, Archivo, Source Serif 4, square corners, ink and red on paper) stays. All three themes (light, dark, sepia) must work for every new screen. Mockups show light, except Sermon mode, which is always dark.
  5. Do not lose data. The live database holds a few notes and highlights. Every schema change is an additive migration with a backfill; nothing is dropped without asking.
  6. Shared database. The Supabase project is shared with another app whose tables are prefixed para_. Never read, alter or drop any para_* object, and scope every policy change to this app's own tables.
  7. Secrets. Never commit .env. Never put an Anthropic key in a VITE_ variable or anywhere the browser or the Electron installer can read it.
  8. Ask before: any destructive SQL, rotating keys, changing the sign-in method, or adding a paid service. The open questions are listed in section 10.
  9. Sample data in the mockups (plan day, counts, sermon timer, map progress) is illustrative. Scripture text and the search counts are real.

Type and shape

5 · Build phases

Phase 1 · Lock down

Blocks everything else

  • Add Supabase Auth and a sign-in screen (method: see section 10). Gate the whole app behind a session.
  • Add user_id to the four existing tables, backfill existing rows to the owner's user id after first sign-in, then replace every "Allow all" policy with owner-only policies for the authenticated role (SQL in section 6).
  • Preferences become one row per user, keyed by user_id; remove PREFS_ID.
  • Create a Supabase Edge Function scholar that verifies the caller's JWT, holds ANTHROPIC_API_KEY as a function secret, takes the model id from a function environment variable, and streams the reply. Route all AI calls through it. Remove the API-key field, bsa_api_key, and every direct call to api.anthropic.com.
  • Electron: remove .env from build.files, delete the ask-scholar handler and the dotenv dependency; the desktop app uses the same Edge Function.
  • Replace supabase/migrations.sql with timestamped files under supabase/migrations/ that reproduce the live schema, including the four preference columns the old file lacks.

Accept when

  • A request with only the anon key returns no rows from, and cannot write to, any of this app's tables.
  • A second test account cannot see the first account's notes or highlights.
  • Existing notes and highlights are still there for the owner.
  • Ask AI works on a fresh browser with no key entered; the built bundle and the Electron package contain no Anthropic key.
  • No para_* table or policy changed.

Phase 2 · Foundations: structure, offline, storage

Makes the rest cheap to build

  • Split the single component into feature folders (src/features/reader, notes, ask, search, today, settings…), shared components, hooks and lib. Theme via CSS variables. Delete App.jsx, App.css and unused assets. Add a router so screens have URLs (for example /read/john/3).
  • Local Bible store: serve kjv.json from public/ (or split per book), load it once, keep it in IndexedDB, and read chapters from there. File shape: {books:[{name, abbrev, chapters:[{chapter:"1", verses:[{verse:"1", text}]}]}]}; chapter and verse numbers are strings.
  • KJV text markup: braces mark translator-supplied words, {it is}, in 17,366 verses; a brace group containing a colon is a margin note, {reproved: or, discovered}, in 6,687 verses. Render supplied words in italics; strip margin notes from the verse and from search (optionally expose them as a footnote).
  • ASV: add a public-domain ASV file in the same shape so it is offline too. Until then, fetch from bible-api.com and cache each chapter in IndexedDB.
  • Offline writes: an IndexedDB outbox for notes, highlights and later tables; apply optimistically, sync when online, show the sync state in the header.
  • Storage: private buckets for recordings, drawings and photos under a per-user path, with matching storage policies; migrate existing drawings; make "Snap Photo" a real capture (<input type="file" accept="image/*" capture>). The notes list selects only the columns it shows.
  • PWA: correct name and colours, remove the orientation lock, bundle fonts and icons, add Workbox runtime caching.
  • Accessibility pass (defect 12), delete with undo toast (defect 11), remove debug logging.

Accept when

  • With the network off after one visit, the installed app opens, reads any KJV chapter, and a highlight or note made offline appears on another device after reconnecting.
  • Every interactive element is reachable and operable by keyboard; no alert() remains.
  • Initial JS bundle does not include the Bible text.

6 · Data model

Existing tables gain an owner; new tables follow the same pattern. Every table has row level security enabled with an owner-only policy unless noted. Treat this as a sketch: check live constraint names before altering, and write each step as its own migration.

-- Phase 1: ownership on existing tables (repeat for highlights, preferences, recordings)
alter table notes add column user_id uuid references auth.users(id) default auth.uid();
-- after the owner has signed in once:
--   update notes set user_id = '<owner uid>' where user_id is null;
--   alter table notes alter column user_id set not null;

drop policy "Allow all" on notes;
create policy "owner" on notes for all to authenticated
  using (user_id = (select auth.uid()))
  with check (user_id = (select auth.uid()));

-- highlights: uniqueness becomes per user (check the existing constraint's real name first)
alter table highlights drop constraint highlights_book_chapter_verse_key;
alter table highlights add constraint highlights_user_verse_key unique (user_id, book, chapter, verse);

-- preferences: one row per user, plus the columns the old migration file is missing
alter table preferences add constraint preferences_user_key unique (user_id);
alter table preferences
  add column if not exists translation text default 'KJV',
  add column if not exists chapter_panel_collapsed boolean default false,
  add column if not exists current_book text,
  add column if not exists current_chapter integer,
  add column if not exists current_verse integer,
  add column if not exists share_handle text;

-- Phase 2: media moves to Storage
alter table recordings add column storage_path text;   -- audio_data becomes nullable, then unused
alter table notes add column drawing_path text, add column photo_path text;

-- Phase 3: notes link to verses; bookmarks
alter table notes add column book text, add column chapter integer,
  add column verse_start integer, add column verse_end integer, add column updated_at timestamptz default now();
create table bookmarks (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id),
  book text not null, chapter integer not null, verse integer,          -- verse null = whole chapter
  created_at timestamptz not null default now(),
  unique (user_id, book, chapter, verse)
);

-- Phase 5: progress, plans, memory
create table reading_progress (
  user_id uuid not null default auth.uid() references auth.users(id),
  book text not null, chapter integer not null,
  read_at timestamptz not null default now(),
  primary key (user_id, book, chapter)
);
create table user_plans (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id),
  household_id uuid,                                   -- set in Phase 10 for a shared plan
  plan_key text not null,                              -- id of a JSON plan in the repo, or 'custom'
  custom_readings jsonb,                               -- [[{book,chapter}, ...] per day] when custom
  started_on date not null default current_date,
  active boolean not null default true
);
create table memory_verses (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id),
  book text not null, chapter integer not null, verse_start integer not null, verse_end integer not null,
  translation text not null,
  interval_days integer not null default 0,
  due_at timestamptz not null default now(),
  last_result text,                                    -- 'shaky' | 'got_it' | 'by_heart'
  created_at timestamptz not null default now()
);

-- Phase 6: saved AI conversations
create table ai_threads  (id uuid primary key default gen_random_uuid(), user_id uuid not null default auth.uid() references auth.users(id),
                          title text, context_ref text, created_at timestamptz not null default now());
create table ai_messages (id uuid primary key default gen_random_uuid(), thread_id uuid not null references ai_threads(id) on delete cascade,
                          user_id uuid not null default auth.uid() references auth.users(id),
                          role text not null, content text not null, created_at timestamptz not null default now());

-- Phase 7: sermon mode
create table sermon_sessions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id),
  title text, started_at timestamptz not null default now(), duration_seconds integer,
  audio_path text, mime_type text, note_id uuid references notes(id) on delete set null
);
create table sermon_pins (
  id uuid primary key default gen_random_uuid(),
  session_id uuid not null references sermon_sessions(id) on delete cascade,
  user_id uuid not null default auth.uid() references auth.users(id),
  offset_seconds integer not null,
  kind text not null,                                  -- 'ref' | 'note' | 'mark'
  book text, chapter integer, verse_start integer, verse_end integer, body text
);

-- Phase 9: threads
create table threads (id uuid primary key default gen_random_uuid(), user_id uuid not null default auth.uid() references auth.users(id),
                      title text not null, created_at timestamptz not null default now());
create table thread_links (
  id uuid primary key default gen_random_uuid(),
  thread_id uuid not null references threads(id) on delete cascade,
  user_id uuid not null default auth.uid() references auth.users(id),
  position integer not null, label text,
  book text not null, chapter integer not null, verse_start integer not null, verse_end integer not null
);

-- Phase 10: households (policies are by membership, not ownership)
create table households (id uuid primary key default gen_random_uuid(), name text not null, created_by uuid not null default auth.uid() references auth.users(id));
create table household_members (household_id uuid not null references households(id) on delete cascade,
                                user_id uuid not null references auth.users(id), display_name text not null,
                                role text not null default 'member', primary key (household_id, user_id));
create table household_questions (household_id uuid not null references households(id) on delete cascade,
                                  passage text not null, day date not null, questions jsonb not null,
                                  primary key (household_id, passage, day));
-- Members may read reading_progress rows of others in the same household for the shared plan's chapters only.
-- Write membership checks as a SECURITY DEFINER helper with a fixed search_path to avoid recursive policies.

Book names in every table use the exact strings in the BOOKS constant ("Psalms", "Song of Solomon", "1 Samuel"…), as the existing highlight rows do.

7 · Core screens

Rebuilds of what the app already does, with the gaps closed.

A1 · Reader with study panel (desktop, 1440 wide)

Behaviour

  • Tapping a verse selects it (ink outline, white fill). It must not write a highlight. Tapping more verses extends the selection; tapping a selected verse deselects it.

Left panel

  • Existing chapter title block, then the active reading plan (name, progress bar, "Mark chapter read"), then counts of highlights, notes and memory verses in this chapter. Collapsible, as today.
  • "Mark chapter read" writes reading_progress and advances the plan if the chapter is today's reading.

Study panel (right, desktop ≥ 1280px; a sheet tab elsewhere)

  • Follows the selected verse. Sections: cross-references (reference + verse text, tap to navigate), words in this verse (English word, original word, transliteration, Strong's number; tap for the lexicon entry), and "Ask about this verse in context".
  • Needs the Phase 6 datasets. Until they are loaded, hide the two data sections rather than showing empty ones.

Behaviour

  • One 10px square per chapter, grouped by book, 929 Old Testament and 260 New Testament (1,189 total). Filled accent = read, white with a grey border = not yet. Finished books show their name in bold.
  • Data comes from reading_progress. Totals in the header are computed, never stored.
  • Tapping a square opens that chapter. On touch screens, tapping a book name opens the chapter picker for that book, because the squares are too small to be reliable touch targets.
  • Give each testament block a text alternative ("Genesis: 12 of 50 chapters read", …) for screen readers.

Actions

  • Open a chapter I have never read: picks a random unread chapter and opens it.
  • Build a plan from the empty squares: creates a personal plan covering every unread chapter in canonical order at a pace the user chooses (1 to 4 chapters a day).

The progress in this mockup is sample data. On phones the two testaments stack and the page scrolls.

When you stop, your pins become one study note with a summary, the key points and one thing to do this week.

Behaviour

  • Launched from Today or from the Notes "New" menu. Always uses the dark theme, and requests a screen wake lock while recording.
  • Starts an audio recording (reuse the existing MediaRecorder code and its iOS fixes). The timer and level bars reflect the live recording.
  • Pin: the text box accepts a reference or free text. If it parses as a reference, the pin stores the reference and shows the verse text from the local Bible; otherwise it is stored as a note. Each pin stores the recording offset in seconds.
  • Mark this moment adds an empty pin at the current offset, to fill in later.
  • Tapping a pin's time button during playback seeks the audio to that offset.
  • Stop and save: uploads the audio to Storage and creates one study note containing the pins in order. When online, the Edge Function adds a summary, key points and one action step drawn only from the pins.
  • Must work with no connection: the session, pins and audio blob go to IndexedDB first and sync when online.

Out of scope

No automatic speech transcription. It would need a separate speech-to-text service; design the tables so a transcript column can be added later.

B3 · Verse card studio (phone)

Verse card
Shape
Paper

Behaviour

  • Opened from "Share as image" with one verse or a short range (cap at about 400 characters; over that, disable the action with an explanation).
  • Render to a canvas at export size: square 1080×1080, tall 1080×1920, wide 1280×720. The on-screen preview is the same canvas scaled down.
  • Four papers: Ink (#181614 ground, #faf9f6 text), Paper (#faf9f6 / #181614), Sepia (#f5efdc / #2c2013), Red (#8a2318 / #ffffff). Text auto-sizes to fit with a minimum size; reference and translation always present.
  • Optional lines: the user's note under the verse, and a handle set once in Preferences.
  • Wait for document.fonts.ready before drawing so Instrument Serif is used.
  • Share uses the Web Share API with a PNG file where supported; otherwise download. "Copy image" uses the async Clipboard API where supported and is hidden where it is not.

Behaviour

  • A thread is a titled, ordered list of passages that trace one idea through Scripture. The list of threads lives under Notes or Today; this is the detail view.
  • Each link has a reference (verse or range), an optional short label, and shows an excerpt from the local Bible. Tapping opens the passage in Read.
  • Add a passage: reference input with the same parser as search. Also offer "Add to thread" in the verse sheet.
  • Reorder by drag handle, with move up/down buttons as the keyboard and screen-reader alternative. Delete with undo.
  • Suggest the next link: sends the thread title and current links to the Edge Function, which returns up to three candidate references with a one-line reason each. Validate every returned reference against the local Bible before showing it; the user picks or dismisses.
  • Turn this thread into a lesson outline: creates a study note with the passages in order, a heading per link and discussion prompts from the AI.

B5 · Memory trainer (phone, working demo)

Memory · verse 1 of 2 due

John 3:16

KJV
Step
Say it aloud at each step. Words drop out a few at a time until only first letters are left, then none.
How did it go?

Behaviour

  • The mockup on the left works: use "Hide more" and "Show more".
  • Four steps: full text; every third word hidden; every other word hidden; first letters only. A hidden word keeps its first letter and punctuation, the rest becomes dots, and it is drawn in the accent colour.
  • Verses enter the queue from "Memorize" in the verse sheet, due immediately.
  • Self-rating schedules the next review: Shaky → 1 day; Got it → 3 days; By heart → 7 days, then doubling on each further "By heart" (14, 28, …, capped at 120). Shaky resets the interval to 1 day.
  • After rating, advance to the next due verse; when none are left, show a done state and return to Today.
  • Text always comes from the translation the verse was saved in.

Behaviour

  • The household shares one reading plan. "Tonight" is that plan's reading for today.
  • The members row shows who has marked tonight's reading as read: a filled square with a check mark, or an empty outlined square. Names come from each member's profile; "[Name]" here is a placeholder.
  • Table questions: three questions for the passage, one each for little ones, teens and adults, generated by the Edge Function from the passage text and cached per household, passage and day so everyone sees the same ones. "New questions" regenerates.
  • Read it aloud: reads the passage with the browser's speech synthesis, with play/pause and a speed control.
  • Members can see each other's read status only. Notes and highlights stay private unless a later phase adds explicit sharing.

9 · Definition of done (every phase)

  • npm run build and ESLint pass with no new warnings; the Vercel preview deploys.
  • Checked at 390px, 820px and 1440px wide, in light, dark and sepia.
  • Keyboard-only pass through every new control; visible focus; text contrast ≥ 4.5:1; state never shown by colour alone.
  • Works offline where the phase says so, and recovers cleanly when the connection returns.
  • Each new table has RLS enabled and a policy; the Supabase security advisor shows no new findings for this app's tables.
  • Migrations are in the repo and match the live schema. No secret is committed.
  • A short entry in a real README.md describing what the phase added and how to run it.
